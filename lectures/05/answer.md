- 取り組んだレベル：基礎
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：
  app/config.py の RAG_TOP_K を5から3に変更した。検索するページ数だけを変更し、モデル（gemini-3.5-flash-lite）と質問「LoRAとは何ですか？」は同一条件とした。変更前後で app.agent --trace を実行し、検索ツールの呼び出し、回答内容、引用根拠、実行時間、トークン数、推定API費用を比較した。  

- 比較した質問と、固定した条件（モデル・対象資料など）：  
  質問：「LoRAとは何ですか？」  
  モデル：gemini-3.5-flash-lite  
  検索対象：第1〜3回の本講義資料  
  変更した設定：RAG_TOP_K のみ（5件→3件）    

- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）： 
 | 評価項目 | 変更前（5件） | 変更後（3件） | 
 |---|---:|---:| 
 | 実行時間 | 3.29秒 | 2.71秒 | 
 | 入力トークン数 | 3,975 | 2,036 | 
 | 出力トークン数 | 228 | 211 | 
 | モデル応答回数 | 2回 | 2回 | 
 | 生成API推定費用 | 0.001492 USD | 0.001138 USD | 
 | 回答の主な引用根拠 | 第2回 PDF p.51・52 | 第2回 PDF p.51・52 | 
  変更前後とも、search_materials が検索語「LoRA」で呼び出され、LoRAは元の重みを固定し、低ランクの行列によって差分を学習する手法であると説明した。  
  検索件数を減らした結果、入力トークン数は約48.8%、実行時間は約17.6%、生成API推定費用は約23.7%減少した。回答の主要な内容と引用ページは維持された。  
  補助的な確認として、検索語「LoRA QLoRA 違い」で検索結果を比較したところ、上位3件は第2回のp.52・p.51・p.60で共通していた。5件の場合に追加されるp.47と第1回p.61は、今回の比較質問に対する直接的な根拠としての重要性が低いと考えられる。  

- 改善した例と、残る失敗・制約：  
  今回の質問では、主要な根拠を維持しながら入力トークン数と費用を削減できた。一方、検索件数を減らすと、複数ページに根拠が分散している質問では必要な情報を取り逃がす可能性がある。  
  また、変更前後の測定は各1回であり、モデルの出力や処理時間にはばらつきがある。今回の数値だけで、検索件数を減らすことによる効果を一般化することはできない。  

- 気づき・疑問：  
  RAGでは取得する資料が多いほどよいとは限らず、質問に必要な根拠を確保しながら、モデルに渡す情報量を調整することが重要だと理解した。  
  一方で、当初はGemini APIの503エラーが繰り返し発生し、変更前の回答を取得するまでに苦労した。直接のモデル呼び出し、検索単体、Pydantic AIによる呼び出しを切り分けて確認した結果、最終的には検索ツール付きエージェントでも正常に回答を取得できたが、503エラーの原因は特定できなかった。  
  今後は、複数の質問と反復実験により、検索件数と回答品質・処理コストの関係を検証したい。
